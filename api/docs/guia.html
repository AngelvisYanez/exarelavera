EXA Contable — API REST

Guía de consumo e integración. Documentación interactiva (Swagger) en /v1/docs

1. Cómo funciona la autenticación

La API acepta tokens de acceso generados desde el panel de administración (Herramientas → Tokens de Acceso a la API). Cada token está asociado a una empresa y puede tener un límite de consultas por día o por mes.

Envía el token en el header Authorization:

Authorization: Bearer TU_TOKEN
Content-Type: application/json
Cada petición consume una consulta de la cuota del token. Si la cuota se agota, la API responde 401 con {"error":"Token inválido o cuota agotada"}.

2. Flujo de autenticación por usuario (login)

Además del token gestionado, existe un flujo de login que devuelve un token de sesión (24 h):

1Obtener empresas del usuario 
POST /v1/auth/empresas
{ "username": "0704206119" }
2Iniciar sesión 
POST /v1/auth/login
{
  "username": "0704206119",
  "password": "123456",
  "empresa": "NOMBRE DE LA EMPRESA"
}
→ { "success": true, "token": "base64(usuario:empresa:time:firma)" }

El token de login también se envía como Bearer. Los tokens gestionados (del panel) funcionan igual y son intercambiables en todas las rutas protegidas.

3. Ejemplos de consumo

curl

# Listar periodos contables
curl -X POST http://localhost:8080/v1/contabilidad/periodos \
  -H "Authorization: Bearer TU_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'

# Crear un cliente (tesorería)
curl -X POST http://localhost:8080/v1/tesoreria/clientes \
  -H "Authorization: Bearer TU_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"Cli_Nom":"Juan Pérez","Bdd":"exa"}'

JavaScript / fetch

const TOKEN = "TU_TOKEN";
const resp = await fetch("/v1/contabilidad/periodos", {
  method: "POST",
  headers: {
    "Authorization": "Bearer " + TOKEN,
    "Content-Type": "application/json"
  },
  body: JSON.stringify({})
});
const data = await resp.json();
console.log(data);

Python

import requests
r = requests.post(
    "http://localhost:8080/v1/contabilidad/periodos",
    headers={"Authorization": "Bearer TU_TOKEN", "Content-Type": "application/json"},
    json={}
)
print(r.status_code, r.json())

4. Catálogo de módulos y procesos

La API se organiza en módulos y cada módulo contiene sus procesos (recursos o acciones). Esta lista se genera automáticamente desde la especificación OpenAPI y coincide con los permisos que se asignan a cada token desde el panel.

5. Formato de respuesta

Todas las respuestas son JSON. Convención general:

{ "success": true, "data": [...], "message": "OK" }
CódigoSignificado
200 / 201Operación exitosa
400Parámetros inválidos o faltantes
401Token ausente, inválido, expirado o cuota agotada
403Token sin permisos para ese módulo/proceso
404Recurso no encontrado
500Error interno del servidor

6. Convenciones y seguridad

  • Identificador de empresa: Emp_Cod. Base de datos distribuida: Bdd.
  • Paginación por page y perPage en los listados.
  • Para consumos por agentes / IA, usa las definiciones LLM (ver sección 7).
  • El endpoint /v1/data/query ejecuta SQL libre: no lo expongas a terceros sin control.
  • Revoca tokens que ya no uses desde el panel. Los tokens expiran si se les configura fecha.
  • Los tokens pueden restringirse a módulos/procesos concretos; si intentan consumir uno no autorizado se responde 403.

7. Definiciones para agentes / LLM

Si un agente o LLM va a consumir la API, usa estos recursos protegidos (requieren un token gestionado válido):

  • /.well-known/ai-plugin.json — manifiesto del agente (requiere Bearer).
  • /v1/llms/llms-full.txt — descripción completa en Markdown (requiere Bearer).
  • llms.txt (raíz) — índice público opcional que enlaza a los recursos protegidos.
